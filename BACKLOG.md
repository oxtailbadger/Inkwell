## Features

- [ ] **Trending articles panel** — pull in what's popular outside the friend group (e.g. Hacker News top stories). Consider feeds or an algorithm if possible.
- [ ] **Custom email templates (sign-up + sign-in)** — Supabase's defaults are a near-empty message whose link points at `<project>.supabase.co`, a different domain from the From address; with a brand-new sender domain that's the most likely reason the first test landed in spam. Write real templates for **Confirm signup** and **Magic link** (Authentication → Emails): who it's from, why they got it, that it expires, and "ignore this if you didn't request it." Two things worth knowing: (1) these live only in the Supabase dashboard, so keep canonical copies in the repo (e.g. `supabase/email-templates/*.html`) and paste them in — otherwise it's the same unversioned-dashboard-config problem as the signup toggle; (2) use `{{ .ConfirmationURL }}`, never a hardcoded domain, so it follows the Site URL. Verify which template a *first-time* signup actually triggers (new vs existing users can use different ones). The OTP item below is the same file, so do them together. Optional, paid: Supabase's custom auth domain so the link host matches the From domain.
- [ ] **OTP code in email for PWA sign-in** — the iOS home-screen PWA has isolated storage, so a magic link that opens in Safari can never sign the installed PWA in; the only fix is letting the user type an emailed code inside the PWA. The same limitation is why a link opened on a *different device* fails (PKCE verifier lives in the requesting browser) — as of 2026-10-10 that failure explains itself on `/login` instead of showing a blank form, but only an emailed code actually fixes it. A code-entry UI existed and was removed 2026-07-10 (DECISIONS.md) because the template sent only a link. **Now unblocked:** custom SMTP is live, so this is just the template. To build: add `{{ .Token }}` to the Confirm-signup and Magic-link templates (see the templates item above), then add a code field to the "Check your inbox" state in `components/AuthForm.tsx` calling `verifyOtp` (the old UI is in git before `f9e13ab`; check the right `type` for the *sign-up* path in Supabase's docs rather than assuming `"email"`). On success navigate with `useRouter().push("/feed")` or an absolute URL — `window.location.href = "/feed"` trips the `no-location-assign-relative-destination` lint rule that CI now enforces. Needs a test for the sign-up/sign-in mapping (see Test gaps). Until then, PWA users must sign in via the browser first.
- [ ] **Tighten DMARC after monitoring** — published as `v=DMARC1; p=none` on 2026-10-10 (monitor only; it satisfies Gmail/Yahoo's "has DMARC" expectation but blocks nothing). Once mail has been flowing cleanly for a few weeks, move to `p=quarantine`, then `p=reject`. Add `rua=` reporting through a DMARC report service rather than a personal address — reports to a mailbox on another domain can be silently dropped without an authorization record. Don't add a second SPF record at the root; Resend's SPF is on its `send.` subdomain by design and a duplicate makes SPF fail.
- [ ] **Add more curated authors** — the `authors` table in Supabase drives the feed. Easy to add new RSS feeds without a code deploy. Candidates: Ezra Klein, Matt Levine (Bloomberg), The Economist briefing.
- [ ] **Article comments / reactions** — a lightweight text reply thread per article so friends can discuss without a group chat. `article_state` (per-user, per-article, RLS scoped to the owning user — see DECISIONS.md) is a ready-made template for a `comments` table's RLS, now that it exists.
- [ ] **Weekly digest email** — a cron-triggered email (Resend or Postmark) with the top-nodded articles from the past 7 days.
- [ ] **Feedback: notify + admin view** — feedback currently lands in the `feedback` table and is read by hand in the Supabase dashboard (see DECISIONS.md). If it gets any volume, add a notification on insert (email/Slack via a Supabase Edge Function or DB webhook) so it isn't missed, and/or a minimal owner-only read UI. Deferred until there's actually feedback to keep up with.
- [ ] **Full-text search** — search across everything ever shared, title + description (article body if Reader view lands). Postgres `tsvector`/`tsquery` with a GIN index makes this nearly free on Supabase; the group's collective memory ("what was that shipping piece from last year?").
- [ ] **Pull quotes** — let the sharer attach a highlighted sentence when submitting ("this is the paragraph that made me send this"). New nullable `pull_quote` column on articles + a textarea in SubmitArticle + styled blockquote on the card. Cheap to build, answers "why should I read this?"
- [ ] **Bookmarklet or browser extension** — desktop capture friction. Start with a bookmarklet (an afternoon: a `javascript:` link that opens `/share?url=` + current page URL — reuses the Web Share Target landing route as-is); only graduate to a Chrome extension if the group wants context menus or one-click submit.
- [ ] **Reader view** — parse article text server-side (Mozilla Readability) and offer a clean in-app reading page. Highest-effort item here and legally gray for paywalled content; pairs with the archive.is habit. Only build if testers ask for it.
- [ ] **Update user email** — let a signed-in user change their login email. Supabase supports `auth.updateUser({ email })` with a confirmation link to the new address; needs a small settings page/modal plus handling for the confirmation state. Note: display names derive from the original email prefix at signup, so decide whether an email change should refresh `profiles.display_name`.

## Path to public launch

Findings from the full acquisition-style code review (2026-07-07, full details in that session's review). These are the changes needed to take Inkwell from a trusted-friends beta to a public-scale launch. Ordered by priority within each tier.

### Launch blockers — do before any public exposure

- [ ] **Enforce the access model in code, not dashboard config** — every RLS read policy is `using (true)` for any authenticated user, so any account can read all shared articles. **Now more urgent:** open self-serve sign-up shipped 2026-07-10 (`/signup`, `shouldCreateUser: true`, see DECISIONS.md), so onboarding no longer requires the owner to hand-add emails — meaning anyone who signs up is inside the shared community. This is acceptable for trusted beta only; before public exposure the fix is an allowlist table checked by RLS, or the invite flow (see Deferred), plus disabling open signup again. The sign-in path still uses `shouldCreateUser: false`. Since 2026-10-10 the database also enforces content limits itself (`supabase/content-constraints.sql`, see DECISIONS.md), so a signed-in user can no longer skip API validation by writing to PostgREST directly — but they can still *read* everything.
- [x] **Custom SMTP before launch** — *done 2026-10-10.* Auth email now goes out through Resend over SMTP from `inkwell-reads.xyz`, replacing Supabase's built-in sender (a few emails/hour). DNS for the domain is hosted at **Vercel** (registrar is Name.com — records added at Name.com are ignored); SPF and DKIM were added by the provider under `send.` / `resend._domainkey.`, and DMARC (`p=none`) at `_dmarc`. See DECISIONS.md. Not yet confirmed: that Supabase → Authentication → Rate Limits was raised from its low custom-SMTP default. The first test email landed in spam; the follow-ups are the custom-template and DMARC items under Features.
- [ ] **CAPTCHA on sign-up/sign-in** — `/signup` is open and unauthenticated; with no bot protection anyone can submit arbitrary addresses. With custom SMTP in place the quota no longer locks real users out in minutes, but the exposure moved rather than vanished: bot signups now spend your *sending reputation* (a burst of bounces to junk addresses is what gets a young domain blocklisted) and your provider's monthly allowance. Supabase Auth has a built-in Turnstile/hCaptcha integration (dashboard setting under Attack Protection + a token passed to `signInWithOtp`); needs a small change to `components/AuthForm.tsx`. Next in line now that SMTP is done.

### Medium priority

- [ ] **Adopt DB migrations** — the `supabase/*.sql` files (eight as of 2026-10-10: `schema`, `nods-schema`, `nod-counts-view`, `article-state-schema`, `authors-schema`, `profiles-schema`, `feedback-schema`, `content-constraints`) are run-by-hand snapshots with implicit ordering; production drift is unverifiable, and the count keeps growing every feature. Move to Supabase CLI migrations or a single canonical dumped schema. Note `content-constraints.sql` already replaces `handle_new_user()` defined in `profiles-schema.sql`, so order matters and "which version is live" is exactly the drift this item is about.
- [ ] **Run the Supabase dashboard linter before launch** — the objects defined in this repo have been audited (2026-10-10): `article_nod_counts` is `security_invoker`, `feed_articles()` is `security invoker` with a pinned `search_path`, and `handle_new_user()` had its EXECUTE revoked from `anon`/`authenticated` (`launch-hardening.sql`). What's left is the part code can't see: run Database → Linter in the Supabase dashboard against the live project and confirm it's clean — anything created by hand in the dashboard won't be in `supabase/*.sql`. Still gates the "enforce the access model in code" blocker: RLS is only trustworthy if nothing routes around it.

### Pre-launch review follow-ups (2026-10-10)

Findings from the pre-deploy senior-engineer review that weren't fixed in the same pass (fixed in that pass: Next.js upgrade, signed-out `/api` 401, DB content constraints; fixed afterwards and removed from this list: feed filtering moved into Postgres, feedback attribution, `article_state` index, security headers, author-feed timeout/link validation, 401 handling in the client, the cross-device link message, and lint + audit in CI — see DECISIONS.md). Roughly in priority order.

- [ ] **Rate-limit the write endpoints, durably** — `articles` POST, `nods`, `feedback`, `profile`, `article-state` have no limits, and the limiter that exists (`fetch-og`, `archive-check`) is an in-memory Map that gives no protection across serverless instances (documented as intentional for ~10 users in DECISIONS.md; open signup ends that). Needs shared state (Upstash/Vercel KV). Limits must also live in the DB layer for direct-PostgREST callers, or accept that the app limiter only covers the app.
- [ ] **Replace `fetchAllTags`' full-table scan** — it selects the `tags` column of *every* article on each feed render (`lib/articles.ts`), so it's O(all articles) and only gets slower. Replace with a distinct-tags view/RPC (`security_invoker`) or a small `tags` table. (The `article_state(user_id)` index half of this item shipped in `launch-hardening.sql`.)
- [ ] **Content-Security-Policy** — the baseline headers shipped (`nosniff`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`; see DECISIONS.md). A CSP is the remaining piece and needs design: article images are hot-linked from arbitrary hosts so `img-src` can't be a short allowlist, and `layout.tsx` has an inline theme-init script that needs a nonce or hash. Roll out as `Content-Security-Policy-Report-Only` first. Pair with `referrerPolicy="no-referrer"` on the hot-linked `<img>`s.
- [ ] **Default display name leaks the email local-part** — the signup trigger makes `display_name = split_part(email,'@',1)`, visible to every user on every article. Fine for friends; with open signup consider a neutral default ("Reader 4821") and letting people choose.
- [ ] **Small correctness items** — fast tag switching can show stale results (no abort/ordering in `loadArticles`, `FeedClient.tsx`); `toLocaleDateString()` in `ArticleCard.tsx` renders in server (UTC) vs. viewer timezone → likely hydration mismatch; "Remove" on your own article has no confirmation and cascades to everyone's nods/state; `request.json()` is unguarded in most routes (malformed JSON → 500) and `article_id`/`id` aren't UUID-validated (→ 500 instead of 400); sharing while signed out loses the shared URL.
- [ ] **No duplicate-link protection** — no unique constraint on `articles.url`, so the same link can be shared repeatedly (by accident or on purpose). Needs URL canonicalization (strip tracking params) to be useful; see MULTI_COMMUNITY.md Option D.
- [ ] **Observability** — console logs only. Add error monitoring (e.g. Sentry) and an uptime check before inviting people you can't message directly. Also set Vercel's function region to match Supabase's — each request makes ~8 sequential Supabase calls, so a region mismatch compounds.
- [ ] **Test gaps** — SQL is now covered against real Postgres (`db-*.test.ts`: constraints, `feed_articles()`, the feedback policy, the signup trigger), but **RLS on the other tables isn't** (`articles`, `nods`, `profiles`, `article_state` policies) — extending `helpers/pg.ts` is cheap now. Still untested: `AuthForm` (the `shouldCreateUser` mapping that opens/closes signup — needs the mapping extracted to a pure function since the repo has no DOM-testing library) and the client components.

## Known limitations / bugs

- [ ] **NYT / WSJ previews always go manual** — Microlink's EPROXYNEEDED is a hard block. No fix short of a paid Microlink plan or a custom proxy. The manual fallback form is the current workaround.
- [ ] **Author RSS cache is 1 hour** — set via Vercel edge cache in `author-articles/route.ts`. New articles won't appear for up to an hour after publish.
- [ ] **Nod count visible to all** — currently nod counts are public. If the group wants anonymity ("I don't want people to know what I've read"), counts would need to be hidden. Now a clean change: the `article_nod_counts` view is `security_invoker = true` (see DECISIONS.md), so tightening `nods`'s SELECT policy propagates through the view instead of being bypassed by it.

## Deferred / someday

- [ ] **Invite flow** — currently access is by manually adding emails in Supabase. A simple invite-by-email flow would make onboarding new friends easier.
- [ ] **Account-backed theme preference** — theme is per-device (`localStorage`) by design (see DECISIONS.md); it doesn't follow a user to another browser/device. If cross-device consistency is wanted later, add a `theme` column to `profiles`, load it server-side in `layout.tsx`/the profile page to apply before paint, and write it through `PATCH /api/profile` alongside the localStorage write (keep localStorage as the pre-paint fast path to avoid a flash). Deferred 2026-07-10 — the one-device-per-friend audience didn't justify the migration + dual source of truth.
